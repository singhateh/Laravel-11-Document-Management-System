## User Roles and Permissions Analysis

### 1. **User Roles in the System**

The application has three main user roles:
- **Admin**: Full system access
- **Owner**: Special privileges for managing the system
- **Manager**: Not explicitly implemented in the current codebase

### 2. **Role Functions and Permissions**

#### **Admin Role**
- **Full system access**: Can view, update, delete, and restore all resources (documents, folders, users, notifications, etc.)
- **Document management**: Access all documents (including private ones), edit, delete, share
- **User management**: Create, update, delete users
- **System management**: Access all areas of the application

#### **Owner Role**
- **Limited system access**: Can view all non-private folders
- **User management**: Can view and update users (but not delete)
- **Document management**: Similar to regular users but with broader folder access

#### **Regular User**
- **Document management**: Create, view, edit, delete, share their own documents
- **Folder management**: Create, view, edit, delete their own folders
- **Sharing**: Can share documents/folders with other users
- **Notifications**: Receive notifications about shared documents and updates

### 3. **Permissions Implementation**

Permissions are implemented through:
1. **Role checks**: Using `$user->isAdmin()` and `$user->isOwner()` methods
2. **Policies**: Each model has a policy class that defines permissions
3. **Gate checks**: Controller methods use `$user->can()` to verify permissions

Key policy files:
- [`DocumentPolicy.php`](app/Policies/DocumentPolicy.php)
- [`FolderPolicy.php`](app/Policies/FolderPolicy.php)
- [`UserPolicy.php`](app/Policies/UserPolicy.php)
- [`StegoDocumentPolicy.php`](app/Policies/StegoDocumentPolicy.php)

### 4. **UI for Role Management**

**Current State**: The application does NOT have a dedicated UI for role management.

**Limitations**:
- No interface to view or edit user roles
- No way to assign roles to users
- No UI to view role permissions

**Backend Support**:
- The `RoleGrant` model exists but is not used
- The `user` table has a `role` column that stores "admin", "owner", or "user"
- The [`UserController.php`](app/Http/Controllers/UserController.php) only handles user search

### 5. **Role Grant System**

The `RoleGrant` model is designed to handle granular role permissions, but it's not implemented. It has fields for:
- `role`: The role name
- `permission`: The permission type (e.g., "view", "edit", "delete")
- `resource`: The resource type (e.g., "document", "folder")
- `user_id`: The user to whom the grant applies
- `is_granted`: Whether the permission is granted or revoked

### 6. **Recommendation**

To implement a complete role management system, you would need to:
1. Create a UI for managing user roles and permissions
2. Implement the `RoleGrant` system to handle granular permissions
3. Add API endpoints for role management
4. Update the frontend to respect role-based UI elements (e.g., hide certain features from non-admin users)

This would allow for more complex permission structures beyond the current simple role checks.

## Key Changes

### 1. Office Document Preview Enhancement

**File Modified**: `resources/js/Components/DocumentPreview.tsx`

**Description**: Added support for previewing Microsoft Office documents (DOC, DOCX, XLS, XLSX, PPT, PPTX) using Microsoft Office Web Viewer.

**Changes Made**:
- Replaced the fallback "cannot be previewed" message with an embedded Office Web Viewer iframe
- Implemented URL encoding to ensure document URLs work with the Office Web Viewer service
- Maintained existing functionality for other file types (images, PDFs, videos, audio, text)
- Added proper frame border and fullscreen support

### 2. Technical Details

The Office Web Viewer integration uses the following URL format:
```
https://view.officeapps.live.com/op/embed.aspx?src=${encodeURIComponent(fileUrl)}
```

This approach:
- Does not require any additional server-side dependencies
- Leverages Microsoft's free, reliable Office viewing service
- Works on all modern browsers that support iframes
- Handles document decryption through existing server-side mechanisms
- Provides a consistent user experience across all document types

## Additional Update - Stego Local Decode Performance

### 1. Ciphertext Storage Path Optimization

Updated Stego encode/decode flow to keep large ciphertext out of MySQL rows for local testing:

- `StegoDocumentService::encode()` now stores ciphertext on local disk at `storage/app/stego/ciphertext/{id}.enc`
- `stego_documents.ciphertext` is now intentionally written as `null`
- `stego_documents.s3_key` stores the local ciphertext path in local/dev flow

Result: metadata queries stay small and avoid loading large base64 blobs.

### 2. Decode Timing Instrumentation

Added per-phase timing logs in `StegoDocumentService::decode()`:

- `db_meta_fetch_ms`
- `db_segments_ms`
- `cipher_ready_ms`
- `decrypt_ms`
- `hash_verify_ms`
- `total_ms`

The log channel entry name is `stego.decode.timing`.

### 3. Query Projection Tightening

Reduced selected columns in Stego list/decode queries to avoid fetching heavy fields unnecessarily:

- `PersistenceService::findStegoDocument()` now explicitly selects decode-required metadata columns
- `StegoWebController` list/decode lookups now select only required fields
- `Api/StegoDocumentController` index/decode/download lookups now select only required fields

### 4. Backward Compatibility

Decode remains compatible with older rows:

- If segments exist, decode reassembles from segment chunks
- If no segments, decode falls back to loading ciphertext from local file path (`s3_key`)
- If local file is missing, decode falls back to legacy DB `ciphertext`

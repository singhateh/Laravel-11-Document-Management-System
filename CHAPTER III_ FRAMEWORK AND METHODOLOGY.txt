CHAPTER III
FRAMEWORK AND METHODOLOGY
This chapter outlines the conceptual framework and methodology for developing StegoLock: A Cloud-Based Secure Digital Document Repository Utilizing Steganographic Encryption with AES and Key Derivation Function. This chapter presents the application’s framework, system architecture, and the models used. The contents of this chapter guided the researchers in developing the application.
3.1 CONCEPTUAL FRAMEWORK
The StegoLock framework is organized into three main stages: Input, Secure Embedding Process, and Output. During the Input stage, the system authenticates users and collects the sensitive document file along with carrier files. In the following stages, the framework applies encryption and, if necessary, performs segmentation, producing stego files ready for secure cloud transmission. The following are the stages and phases of StegoLock:
  

3.1.1 INPUT STAGE
In the Input stage, the StegoLock application first authenticates the user and validates their role before accepting any file inputs. Unlike traditional systems that require a passphrase for each document operation, StegoLock implements a Master Key Derivation (MKD) system that provides enhanced usability and security.
User Authentication and Role Validation:
The system enforces strict authentication requirements. Users must provide their username and password credentials to log in. The API Gateway validates these credentials against stored user accounts and derives a Master Key using PBKDF2-SHA256 with 100,000 iterations and a server-side salt [106], [107]. Upon successful authentication, the system issues a Laravel Sanctum token that remains valid for the session duration (typically 8 hours). This token identifies the user for subsequent API requests and is paired with a server-side session that holds the derived Master Key.
Only authenticated users with valid session tokens can proceed with document operations. The system enforces three distinct user roles: Document Owners can upload, retrieve, and share documents; Document Viewers have read-only access to documents shared with them; System Administrators can manage users and view audit logs, but cannot access document content [108].
File Input Requirements:
After successful authentication, the system requests two types of files from the user: the sensitive document file and the carrier file(s). The document file must be in a standard format, such as PDF, DOCX, or TXT, to ensure compatibility across devices and platforms. The carrier file must be in image format (JPEG or PNG) and serve as the host for the encrypted document segments via LSB steganography. Each carrier image must be sized appropriately to hold its assigned ciphertext chunk; the system calculates the minimum required dimensions and informs the user if additional or larger images are needed.
Master Key Derivation System:
A critical innovation in StegoLock’s design is the elimination of per-document passphrase requirements. The Master Key, derived during authentication, serves as the foundation for all subsequent document encryption keys. For each document operation, the system derives a unique Document Encryption Key (DEK) by applying PBKDF2 with 10,000 iterations to the combination of the Master Key and a document-specific salt (derived from the document ID) [106], [107]. This approach provides several advantages: users authenticate only once per session, document-specific keys remain cryptographically independent, and the system maintains security while significantly improving user experience.
3.1.2 SECURE EMBEDDING PROCESS STAGE
The Secure Embedding Process stage consists of five phases: Master Key and Document Key Derivation, Encryption, Segmentation (if needed), Steganographic Embedding, and Finalization. During this stage, the document is encrypted, potentially segmented, and hidden within carrier files. This multi-phase approach ensures both confidentiality and concealment.
3.1.2.1 PHASE ONE: MASTER KEY AND DOCUMENT KEY DERIVATION
The first phase establishes the cryptographic foundation for document protection. The system receives the Master Key Token (Laravel Sanctum) from the authenticated user session and derives a unique Document Encryption Key (DEK) for the document.
The DEK is generated using PBKDF2-SHA256 with 10,000 iterations applied to the Master Key, along with a document-specific salt derived from the document ID [106], [107]. This ensures the same document always uses the same key while different documents remain cryptographically independent, providing strong isolation.
A random 12-byte Initialization Vector (IV) is also generated for AES-GCM encryption, ensuring identical plaintexts produce different ciphertexts and preventing pattern analysis attacks [109]. The IV is not secret and is stored with the encrypted data.
The resulting 256-bit DEK and IV are used for encryption. The DEK exists only in memory during the process and is never stored or transmitted, maintaining strong protection against key-guessing attacks.
3.1.2.2 PHASE TWO: ENCRYPTION
The second phase prepares and encrypts the document through a three-step pipeline: compression, encryption, and encoding. First, the plaintext is compressed using gzip level 6 (gzcompress), typically reducing size by 60–80%. Compression occurs before encryption because encrypted data cannot be compressed. A boolean compressed flag is stored to support backward-compatible decryption.
Next, the compressed data is encrypted using AES-256-GCM to ensure confidentiality and integrity [110]. The process uses the compressed plaintext, the 256-bit DEK from Phase One, and a 12-byte random IV. AES-256-GCM generates a ciphertext and a 16-byte authentication tag, which serves as a cryptographic signature to detect tampering during storage or transmission [110].
During retrieval, the system verifies the authentication tag before decryption. If validation fails, the operation is rejected, and a security alert is logged, indicating possible data modification.
Finally, the ciphertext is base64-encoded, which is more efficient than hexadecimal encoding. The base64 ciphertext, IV, authentication tag, dek_salt, and a SHA-256 hash of the original plaintext together form the encrypted record stored in the database. This ensures that even if attackers extract the data, the original document remains inaccessible without the correct DEK.
3.1.2.3 PHASE THREE: SEGMENTATION
The third phase determines whether the encrypted document fits within a single carrier file or requires segmentation across multiple carrier files. The Segmentation Service analyzes the size of the encrypted payload and compares it against the total capacity of available carrier files.
Capacity Analysis:
The system calculates image carrier capacity based on pixel dimensions and color channels. For a standard RGB image, the LSB capacity in bytes is: (width × height × 3) ÷ 8. For example, a 1,000 × 1,000 pixel image provides approximately 375,000 bytes of embedding capacity. StegoLock employs a one-image-per-chunk assignment strategy: each 2 MB ciphertext chunk is assigned to exactly one carrier image. The system verifies that the assigned carrier image is large enough to hold its chunk before embedding proceeds. If a carrier is too small, the system calculates the minimum required image dimensions and reports these to the user.
Segmentation Decision:
If the encrypted payload size is less than or equal to the carrier capacity, the system proceeds with single-carrier embedding. If the payload exceeds the capacity of a single carrier, the system splits the encrypted data into multiple segments.


Segmentation Process:
When segmentation is required, the system decodes the base64 ciphertext and divides the raw binary into 2 MB chunks [112], [117]. Each segment is tagged with metadata, including segment_index (0-based position), total_segments (total count), and encrypted_size (exact byte count of the binary chunk). The encrypted_size value is critical during extraction: it tells the Python LSB extractor precisely how many bytes to read from the stego-image, preventing over-extraction of padding or noise. This metadata ensures proper reassembly during document retrieval.
The segmentation approach provides several benefits: it enables embedding of large documents across multiple carrier files, maintains cryptographic security by operating on encrypted data rather than plaintext, and ensures reliable reassembly through indexed segment tracking. The segment metadata is stored separately in the database, allowing the system to reconstruct the correct order during extraction.
3.1.2.4 PHASE FOUR: STEGANOGRAPHIC EMBEDDING
The fourth phase performs the actual data hiding operation. StegoLock supports image-based LSB steganography exclusively, embedding each ciphertext chunk into a dedicated carrier image. This focus on a single carrier type ensures consistent quality control, deterministic extraction, and simplified implementation. Embedding occurs after the document has been encrypted, compressed, encoded, and segmented, ensuring that only the processed ciphertext is hidden within carrier images.
Image Steganography (LSB):
Encrypted document segments are embedded into JPEG and PNG images using Least Significant Bit (LSB) steganography [111]. This method modifies the least significant bit of pixel color values. Since each pixel contains three 8-bit channels (Red, Green, Blue), changing an LSB (e.g., 255 → 254) creates a difference that is imperceptible to the human eye. Encrypted data is embedded in the LSBs of multiple pixels.
The embedding process runs pixel by pixel and channel by channel. Each byte of encrypted data is split into 8 bits, and each bit is written into the LSB of 8 consecutive color channel values (e.g., embedding 10110011 by adjusting the 8 LSBs).
After embedding, the system calculates the Peak Signal-to-Noise Ratio (PSNR) to ensure imperceptibility [119]. A PSNR of 40 dB or higher indicates the changes are visually undetectable. If PSNR falls below this threshold, the system warns the user and suggests using a larger carrier image or splitting the document into more segments.
Carrier File Integrity:
To prevent the carrier file from becoming corrupted, StegoLock includes a safeguard mechanism. The system ensures the carrier file remains fully functional: images can still be viewed normally, audio can be played without noticeable distortion, and text can be read without visible alterations. This functionality preservation is essential for maintaining stealth—stego-files that appear damaged or unusual attract attention from potential attackers [118].
PSNR serves as the primary user assurance mechanism for image carriers. Displaying this metric after embedding provides transparency into embedding quality. A PSNR of 40 dB or above indicates that the stego-image is visually indistinguishable from the original. If PSNR falls below this threshold, the system alerts the user to use a larger carrier image or split the document into more segments.
3.1.2.5 PHASE FIVE: FINALIZATION AND CLOUD PREPARATION
After the encrypted segments have been successfully embedded into the carrier files, the modified stego files have reached their final form. The Finalization phase organizes these carriers and their metadata, preparing them for cloud storage.
Metadata Storage:
The Persistence Service stores comprehensive metadata for each document and its associated stego files in the database. This metadata includes: document owner ID, original filename, file size, segment count (if segmented), creation timestamp, carrier type for each segment, quality metrics (PSNR/SNR values), and S3 storage URLs. Additionally, the system records segment metadata, including segment_index, total_segments, encrypted_size, and assembly order. This metadata enables reliable document retrieval and reassembly.
Role-Based Access Control:
For documents shared with other users, the system stores role-grant records mapping document owners to viewers. The role_grants table contains entries specifying which users (viewer_user_id) have been granted access to which documents (document_id) by which owners (owner_id). This information is consulted during document retrieval to enforce access control policies.
Audit Logging:
The system logs all document operations to the access_logs table, recording user ID, action type (upload, retrieve, grant, revoke), document ID, success status, timestamp, and IP address. This audit trail provides accountability and enables security monitoring. If any anomalous access patterns are detected (such as repeated failed retrieval attempts), administrators can investigate potential security incidents.
Cloud Preparation:
In the final step of this phase, the stego-images are stored via the configured storage disk (local filesystem by default, switchable to cloud storage via the stegolock.storage_disk configuration key). The output is a set of standard-looking image files (PNG or JPEG) that contain the encrypted document segments. These files can be extracted only by a user with the correct authentication credentials and system access. The storage path for each stego-image is recorded in the database rather than storing any S3 URL directly, keeping storage backend concerns outside the database schema.
3.1.3 OUTPUT AND RETRIEVAL STAGE
The Output and Retrieval Stage encompasses two complementary processes: storing documents securely in cloud storage and retrieving them when needed. This stage involves secure transmission, server-side encryption, access control enforcement, and the complete retrieval workflow from cloud download to document delivery.
3.1.3.1 OUTPUT PROCESS (STORAGE)
After the documents are processed through the Secure Embedding Process, stego-images are persisted via the Cloud Storage Service, which abstracts the underlying storage backend. By default, StegoLock uses local filesystem storage for development and testing, but can be configured to use any Laravel-compatible storage driver (such as S3-compatible object storage) by changing the stegolock.storage_disk configuration value without modifying application code.
Cloud Upload Process:
The Cloud Storage Service stores each stego-image to a unique path that encodes the document ID and segment index (e.g., stego/{document_id}/segment_{index}.png). Before storage, the service computes a SHA-256 hash of the stego-image file and records this hash in the database alongside the storage path. This hash is later used during retrieval to verify file integrity.
During upload, the service implements retry logic to handle transient network failures. If an upload fails due to temporary network issues, the system automatically retries up to 3 times with exponentially increasing backoff intervals. If all retry attempts fail, the system rolls back, deleting any partially uploaded segments and marking the document operation as failed.
Server-Side Encryption:
Because the document content is already protected by AES-256-GCM encryption before steganographic embedding, stego-images at rest are protected by multiple layers. Even if an attacker gains unauthorized access to the storage volume, they encounter image files that appear visually normal but contain encrypted ciphertext that cannot be decrypted without the user's Master Key. When cloud storage is configured, operators may also enable server-side encryption at the storage provider level, providing an additional defense-in-depth layer.
Stealth and Security:
Once stored, stego-images appear as normal image files to interceptors or unauthorized parties. This reduces the likelihood of being targeted by cyberattacks, as attackers often prioritize files that are obviously encrypted or protected. An individual who intercepts or gains unauthorized access to a stego-file would only see a standard image, audio track, or text document. Without knowledge of StegoLock’s steganographic encoding scheme and without the correct authentication credentials to derive the Document Encryption Key, the encrypted payload remains hidden and protected.
Quality Metrics Display:
After a successful upload, the system returns the calculated PSNR values to the client application through the API Gateway. The React-based user interface displays these metrics to the user, providing transparency and assurance. Users can verify that their stego-images maintain acceptable imperceptibility: a PSNR of 40 dB or above indicates imperceptible visual modification.
These quality metrics serve multiple purposes: they provide users with confidence that their stego-files will not attract attention, enable them to make informed decisions about carrier file selection, and demonstrate the system’s commitment to maintaining steganographic imperceptibility.
3.1.3.2 RETRIEVAL PROCESS (ACCESS)
The Retrieval Process enables authorized users to recover their original documents from cloud storage. This process mirrors the output process in reverse: downloading stego-files, extracting encrypted data, reassembling segments, and decrypting to recover the plaintext document.
Authentication and Authorization:
The system enforces strict access control during document retrieval. Only users with appropriate permissions can retrieve documents: Document Owners can retrieve any document they uploaded, Document Viewers can retrieve only documents explicitly shared with them by the owner, and System Administrators cannot retrieve document content but can view metadata and audit logs.
When a user requests document retrieval, the API Gateway validates their Sanctum token, queries the database to verify ownership or role-grant access, and either authorizes the request or returns a 403 Forbidden error. This enforcement occurs before any decryption or extraction operations begin, ensuring that unauthorized users cannot even attempt to access encrypted data.
Stego-File Download:
Once authorization is confirmed, the Cloud Storage Service retrieves the stego-images from the configured storage disk using the paths recorded in the database. The service retrieves all carrier images associated with the document, whether single-carrier or multi-carrier. During retrieval, the system verifies file integrity by computing a SHA-256 hash of each downloaded image and comparing it against the hash stored in the database at upload time. If a hash mismatch is detected, indicating data corruption or tampering, the system logs an alert and returns an error to the user.
Steganographic Extraction:
After a successful download, the Steganography Service extracts the encrypted data from the carrier files using the appropriate method for each carrier type. For image carriers, the Python LSB extraction script reads exactly encrypted_size bytes from the stego-image by scanning the RGB channels pixel-by-pixel and reconstructing the embedded data bit-by-bit. The encrypted_size value stored per segment is essential here: it prevents the extractor from reading beyond the embedded payload into unmodified pixel data [111].
The extraction process is deterministic: as long as the carrier file has not been modified, the same encrypted data that was embedded during upload is extracted. This ensures data integrity throughout the storage and retrieval cycle.
Segment Reassembly:
If the document was segmented across multiple carriers during upload, the Segmentation Service reassembles the segments into the complete encrypted payload. The service sorts segments by their segment_index metadata, ensuring they are concatenated in the correct order. It verifies that the total size matches the stored metadata and that all segments are present. If any segment is missing or the size does not match, the system returns an error indicating incomplete data [112], [117].
Document Decryption:
Once the encrypted payload is reconstructed, the Cryptography Service decrypts it to recover the document. The service derives the same Document Encryption Key (DEK) using PBKDF2 with the Master Key from the user’s session token and the document-specific salt. It then extracts the IV and authentication tag and performs AES-256-GCM decryption [110].


Before returning plaintext, the system verifies the authentication tag. If valid, the document is returned; if invalid, the system rejects the operation, logs a security alert, and reports an error, indicating possible tampering [110].
If the stored compressed flag is true, the decrypted data is decompressed using gzuncompress. The system then verifies the SHA-256 hash of the recovered plaintext against the original hash to ensure end-to-end integrity.
Finally, the DEK is securely wiped from memory using sodium_memzero(), preventing recovery of key material after the operation completes.
Audit Logging and Document Delivery:
The Persistence Service logs the retrieval operation to the access_logs table, recording the user ID, action type (retrieve), document ID, success status, timestamp, and IP address. If tampering was detected during decryption, an additional entry is made to the security_alerts table for investigation.
Finally, the API Gateway returns the plaintext document to the client application over HTTPS. The user interface displays a download button or document preview, allowing the user to download or view their original document. The complete retrieval process—from authorization to document delivery—ensures that only authorized users can access documents and that any tampering or corruption is immediately detected and reported.


3.2 DEVELOPMENT METHODOLOGY  

StegoLock’s development follows an Agile methodology with iterative sprints, continuous testing, and incremental feature delivery. This approach ensures flexibility to adapt to emerging requirements while maintaining security and quality standards [115], [116].

Sprint Structure:
The development process is organized into two-week sprints. Each sprint begins with sprint planning, where the team selects user stories from the product backlog, estimates effort, and commits to deliverables. During the sprint, daily stand-up meetings ensure coordination and identify blockers. At the end, the team conducts a sprint review to demonstrate completed features and a sprint retrospective to identify process improvements.

Feature Development Process:
Each feature progresses through multiple stages: requirements gathering, design and architecture review, implementation, unit testing, integration testing, security testing, code review, deployment to staging, user acceptance testing, and finally deployment to production. This ensures that security and quality are validated at multiple checkpoints before features reach end users.

Testing Strategy:
The testing strategy encompasses multiple levels. Unit tests validate individual functions and methods, particularly cryptographic operations (AES-256-GCM encryption/decryption, PBKDF2 key derivation, authentication tag validation). Integration tests validate service-to-service communication (API Gateway to services, database services, Cloud Storage Service to S3). End-to-end tests validate complete workflows (user authentication, document upload, retrieval). Security tests validate the correctness of encryption, steganographic imperceptibility (PSNR ≥ 40 dB for images), access control enforcement, and tamper detection.

Continuous Integration/Continuous Deployment (CI/CD):
The project uses automated CI/CD pipelines. On every code commit, the system automatically runs unit tests, integration tests, static code analysis (linters, security scanners), and builds container images. Successful builds are deployed to staging environments for further testing. After passing user acceptance tests, changes are promoted to production through controlled deployment procedures with rollback capabilities.

Security-First Development:
Security considerations are integrated throughout the development process. Code reviews specifically examine cryptographic implementations, key management practices, access control logic, and input validation. Threat modeling sessions identify potential attack vectors and inform defensive coding practices. Regular security audits by external reviewers provide independent validation of security measures [120].

Iterative Refinement:
Based on testing results and performance observations, iterative updates are implemented. These updates address emerging issues (bug fixes and performance optimizations), optimization opportunities (improved algorithms and reduced resource consumption), and advancements in related technologies (updated cryptographic standards and improved steganographic techniques). This ensures the application stays current and effective [120].

3.3 ETHICAL CONSIDERATION
3.4.1 Core Purpose and Development Ethics:
StegoLock was developed with a primary focus on the legitimate protection of digital documents from interception and unauthorized exposure. To ensure the highest ethical standards during the research and testing phases, the team used only synthetic or publicly available datasets. At no point was real-world confidential or personal organizational data processed, ensuring the development process remained risk-free and ethically sound. The system is designed to support legitimate use cases such as protecting sensitive business documents, securing personal information, and enabling confidential communications for authorized users.
3.4.2 Privacy by Design:
The commitment to privacy is rooted in a “privacy-by-design” architecture. To protect user integrity, sensitive materials—including documents, credentials, and encryption keys—are never stored or transmitted in plaintext. User passphrases are used strictly for key derivation and are never retained by the system. Furthermore, derived keys exist only temporarily in volatile memory during active operations and are discarded immediately after use, effectively eliminating the risk of exposure or unauthorized reuse.
The Master Key Derivation system enhances privacy by eliminating the need to store per-document passphrases or keys. The Master Key is derived on demand from the user’s password and exists only for the duration of the authenticated session. Document Encryption Keys are similarly derived on demand and discarded immediately after use. This approach ensures that no long-term key material is stored, reducing the attack surface for key compromise.
3.4.3 Security Controls and Responsible Use:
StegoLock is intended to facilitate secure information handling rather than provide a means for concealing illicit activity. To prevent misuse, the system restricts functionality to authenticated, authorized users through robust access controls. These layers of verification ensure that only individuals with explicit permissions can encrypt or retrieve data, promoting a culture of accountability.
The system implements comprehensive audit logging that records all document operations, including uploads, retrievals, access grants, and access revocations. These audit logs enable security monitoring and forensic investigation if misuse is suspected. System administrators can review access patterns and identify anomalous behavior.
3.4.4 Legal Compliance and User Accountability:
Finally, the deployment of StegoLock is contingent upon adherence to local and international legal standards. Users and organizations are responsible for ensuring compliance with relevant data protection regulations, such as the GDPR (General Data Protection Regulation) and HIPAA (Health Insurance Portability and Accountability Act), as well as jurisdiction-specific laws regarding the export and use of cryptographic software.
Organizations deploying StegoLock must implement appropriate data governance policies, including data retention schedules, user access reviews, and incident response procedures. Users must acknowledge acceptable use policies that prohibit using the system for illegal purposes. By establishing these clear ethical and legal boundaries, StegoLock provides a framework for secure, lawful, and accountable document management.
